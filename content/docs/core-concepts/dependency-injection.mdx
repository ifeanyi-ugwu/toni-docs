title: Dependency Injection
description: How Toni's DI container resolves, instantiates, and shares providers.

Toni includes a built-in dependency injection (DI) container. It resolves the dependency graph at startup, instantiates providers in the correct order, and wires everything together before the first request arrives.

<Bridge>
This is the same container-based DI that NestJS uses. In NestJS, the container is managed by the framework's `Injector`. In Toni, the equivalent is `ToniContainer`, which you never interact with directly — `ToniFactory` drives it.

The key concepts (tokens, scopes, the graph resolution) work the same way.
</Bridge>

## How resolution works

When `ToniFactory::create` runs:

1. The module tree is scanned recursively from the root module
2. Each module's `providers` and `controllers` are registered with their dependency lists
3. A dependency graph is built from the `#[inject]` field and `#[new]` parameter declarations
4. The graph is topologically sorted — providers with no dependencies are instantiated first
5. Each subsequent provider receives already-instantiated dependencies

Any failure in this phase — a missing provider, a circular dependency — is logged as a critical initialization error and the process exits with status 1. There's no runtime failure.

## Provider tokens

Every provider is identified by a **token**. The default token is the fully-qualified type name (`std::any::type_name`) — when you write `providers: [UsersService]`, the token is something like `"my_app::users::UsersService"`, and that's the string you'll see in resolution errors. An untagged `#[inject]` field resolves by its type's token; `#[inject("TOKEN")]` resolves by an explicit string token.

Custom tokens let you register multiple providers of the same type under different names, or register non-struct values:

```rust
#[module(
    providers: [
        UsersService,
        provider_value!("APP_NAME", "MyApp".to_string()),
        provider_factory!("DB_POOL", || create_pool()),
        provider_alias!("Users", UsersService),         // alternate name for same service
        provider_token!("PRIMARY_DB", DatabaseService), // custom token for a type
    ],
)]
pub struct AppModule;
```

See [Provider Patterns](/docs/core-concepts/provider-patterns) for full coverage.

## Module scoping

Providers are scoped to their module. A module's providers are **not** visible to other modules unless explicitly exported.

```
AppModule
├── UsersModule
│   ├── providers: [UsersService]     ← private to UsersModule
│   └── exports: [UsersService]       ← now visible to importers
└── OrdersModule
    ├── imports: [UsersModule]         ← can now inject UsersService
    └── providers: [OrdersService]
```

This scoping is enforced at startup. Attempting to inject a provider that isn't in scope causes a clear error during the scan phase.

## Accessing the container at runtime

After the application is created, you can pull instances directly from the container. This is useful for scripting, CLI tools, and testing.

```rust
let app = ToniFactory::create(AppModule).await;

// Get by type, searching all modules
let users_service = app.get::<UsersService>().await?;

// Get by type from a specific module
let service = app.get_from::<UsersService>("UsersModule").await?;

// Get by custom token
let db_pool = app.get_by_token::<Pool>("DB_POOL").await?;

// Get by custom token from a specific module
let db_pool = app.get_from_by_token::<Pool>("AppModule", "DB_POOL").await?;
```

## Standalone application context

For workers, cron jobs, CLI commands, and tests — situations where you want the DI container without an HTTP server:

```rust
use toni::ToniFactory;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut ctx = ToniFactory::create_application_context(AppModule).await;

    // Resolve services normally
    let users_service = ctx.get::<UsersService>().await?;
    let count = users_service.count().await;
    println!("Total users: {count}");

    // Runs shutdown lifecycle hooks
    ctx.close().await;

    Ok(())
}
```

`create_application_context` initializes the full DI container and runs all lifecycle hooks, but doesn't start an HTTP server. `close()` returns `()` — it runs the shutdown hooks unconditionally.

`get` refuses request-scoped providers, since there is no active request. To exercise a request-scoped or transient provider outside a handler, `resolve` builds it against a synthetic request:

```rust
let parts = http::Request::builder().body(()).unwrap().into_parts().0;
let service = ctx.resolve::<RequestScopedService>(&parts).await?;

// or by custom token
let service = ctx.resolve_by_token::<RequestScopedService>("TOKEN", &parts).await?;
```

## How instances are built

By default the container builds each provider directly from its fields: `#[inject]` fields are resolved from the graph, `#[default(expr)]` fields get their expression, untagged fields get `Default::default()`. No constructor is involved:

```rust
#[injectable]
pub struct OrdersService {
    #[inject]
    users_service: UsersService,
    #[inject]
    logger: LoggerService,
    #[default("default".to_string())]
    internal_value: String,
}
```

Tagging a constructor with `#[new]` switches to constructor injection: the container resolves each parameter and calls the function, so dependencies can be consumed without being stored. See [Services & Providers](/docs/core-concepts/services) for when to prefer each.

## Circular dependencies

Providers resolve by topological sort, one module at a time. A cycle within a single module — `ServiceA` injects `ServiceB`, `ServiceB` injects `ServiceA`, both declared in the same module — is caught during the sort and aborts startup with status 1:

```
Circular dependency detected for provider: my_app::services::ServiceA
```

A cycle that spans two modules is invisible to the per-module sort and surfaces later, when the container cannot build either side:

```
Cannot resolve dependencies for modules: ["ModuleA", "ModuleB"]. Possible circular dependency or missing global provider.
```

Either message points to a genuine construction cycle. The fix is to break it.

<Bridge>
NestJS breaks a cycle with `forwardRef`. Toni has no equivalent and needs none: `forwardRef` defers a class reference that is `undefined` at module-evaluation time, but Toni identifies providers by string token and resolves them at runtime, so a reference is never undefined and there is nothing to defer. A reported cycle is always a real construction cycle, not a language artifact.
</Bridge>

### Breaking a cycle

**Extract the shared logic.** Move what both services need into a third provider that each depends on. Neither service then depends on the other, and the cycle disappears. A mutual dependency is usually a sign the two services share a responsibility that wants its own home, so this is the right fix for most cycles.

**Resolve one side lazily with `ModuleRef`.** When the dependency is genuinely bidirectional, inject [`ModuleRef`](/docs/api-reference/core#di-utilities) into one side instead of the provider itself, and fetch the counterpart at call time:

```rust
#[injectable]
pub struct ServiceA {
    #[inject]
    b: ServiceB,
}

#[injectable]
pub struct ServiceB {
    // instead of `#[inject] a: ServiceA`, which would close the cycle
    #[inject]
    module_ref: ModuleRef,
}

impl ServiceB {
    pub async fn notify_a(&self) {
        if let Ok(a) = self.module_ref.get::<ServiceA>().await {
            a.on_event();
        }
    }
}
```

`ServiceB` no longer depends on `ServiceA` at construction, so the container builds `ServiceB` first and the cycle never forms. Both instances exist by the time `notify_a` runs, and `get` returns `ServiceA` from the current module; chain `.global()` before `.await` to widen the search to exported and global providers.
