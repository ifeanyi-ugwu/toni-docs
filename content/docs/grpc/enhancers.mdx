Guards, interceptors, and error handlers are ordinary DI providers applied to a `#[grpc_methods]` impl via `#[use_*]` attributes — at the impl level (every method) or per method:

```rust
#[grpc_methods]
#[tonic::async_trait]
#[use_guards(AuthGuard)]                       // every method
#[use_error_handlers(QtyErrorHandler)]         // every method
impl Orders for OrdersGrpcService {
    #[use_guards(AdminGuard)]                  // this method only
    #[use_interceptors(LoggingInterceptor)]
    async fn create(&self, /* ... */) { /* ... */ }
}
```

Each provider registers by implementing the corresponding trait against `GrpcContext` — there is no marker attribute. Declare `#[injectable]`, implement the trait, list the provider in the module, apply with `#[use_*]`.

The pipeline per call: guards → interceptors → handler → error handlers (on `Err` or panic). Error handlers are covered in [error handling](/docs/grpc/error-handling).

## GrpcContext

gRPC payloads are method-typed protobuf messages and can't sit in a non-generic struct, so `GrpcContext` holds only what every enhancer can name without a type parameter — there is no request body on it:

| Accessor | Returns |
|---|---|
| `method()` | `&str` — proto trait + Rust method name, e.g. `"Orders/create"` |
| `headers()` | the inbound metadata map (`&HashMap<String, String>`) |
| `header(key)` | `Option<&str>` |
| `peer()` | `Option<SocketAddr>` |

Only ASCII metadata is captured into `headers()`; binary (`-bin`) entries are skipped. `GrpcContext` also implements `HandlerContext`, and `metadata()`, `extensions()`, `cache()`, and `cancellation()` work as on the other transports.

`metadata()` is not the wire metadata — that is `headers()`. It returns what `#[set_metadata]` declared: the attribute goes on the `#[grpc_methods]` impl (every method) or on an individual method, and guards, interceptors, and error handlers read it back through `ctx.metadata()`. The handler never sees it.

The handler never sees the context at all — it keeps the plain tonic signature. To hand a value from an enhancer to the handler, insert it into `ctx.extensions()` (the bag mutates through `&self`); the macro rides the bag on the tonic request, and the handler adopts it from there:

```rust
// in a guard or interceptor
ctx.extensions().insert(AuthenticatedUser { id });

// in the handler
let user = toni::context::Extensions::adopt(request.extensions())
    .get::<AuthenticatedUser>();
```

Note the naming split: `#[use_*]` attributes key on the bare Rust method name (`create`), `ctx.method()` returns `"Orders/create"`, and the tracing span's `pattern` field carries the full wire path (`"toni_examples.orders.Orders/Create"`).

## Guards

A guard implements `Guard<GrpcContext>`. The resolved chain runs before the handler; a `false` return short-circuits the call with `PermissionDenied`:

```rust
use toni::GrpcContext;
use toni::traits_helpers::Guard;

#[injectable]
pub struct AuthGuard {}
impl AuthGuard {}

#[toni::async_trait]
impl Guard<GrpcContext> for AuthGuard {
    async fn can_activate(&self, ctx: &GrpcContext) -> bool {
        matches!(ctx.header("authorization"), Some("Bearer secret-token"))
    }
}
```

Method-level guards **stack on** service-level guards, service level first. With `#[use_guards(AuthGuard)]` on the impl and `#[use_guards(AdminGuard)]` on `create`, a call to `create` must pass both; other methods only need `AuthGuard`.

## Interceptors

An interceptor implements `Interceptor<GrpcContext, GrpcHandlerResult>` — `GrpcHandlerResult = Result<(), GrpcStatus>` is what a gRPC call answers with — and wraps the user delegation. Whatever `intercept` returns is the answer, whether it came from `next.run(ctx).await` or from the interceptor itself:

```rust
use toni::{GrpcContext, GrpcHandlerResult};
use toni::traits_helpers::{Interceptor, InterceptorNext};

#[injectable]
pub struct LoggingInterceptor {}
impl LoggingInterceptor {}

#[toni::async_trait]
impl Interceptor<GrpcContext, GrpcHandlerResult> for LoggingInterceptor {
    async fn intercept(
        &self,
        ctx: &GrpcContext,
        next: Box<dyn InterceptorNext<GrpcContext, GrpcHandlerResult>>,
    ) -> GrpcHandlerResult {
        tracing::info!(method = %ctx.method(), "before");
        let answer = next.run(ctx).await;
        tracing::info!(method = %ctx.method(), "after");
        answer
    }
}
```

Method-level interceptors **nest inside** service-level ones:

```
service:before → method:before → handler → method:after → service:after
```

To short-circuit with a typed status, return it without calling `next.run`:

```rust
#[toni::async_trait]
impl Interceptor<GrpcContext, GrpcHandlerResult> for DenyInterceptor {
    async fn intercept(
        &self,
        _ctx: &GrpcContext,
        _next: Box<dyn InterceptorNext<GrpcContext, GrpcHandlerResult>>,
    ) -> GrpcHandlerResult {
        Err(toni::GrpcStatus::permission_denied("blocked by interceptor"))
    }
}
```

## No pipes

`#[use_pipes]` is not supported on `#[grpc_methods]`. The proto payload is method-typed and can't sit in the non-generic `GrpcContext`, and a headers-only pipe adds no expressive power over interceptors. Inbound headers are read-only; to hand data to a later stage or the handler, attach it to `ctx.extensions()`.

## Scope and globals

- **Request-scoped enhancers work.** A gRPC call is an execution like any other: an enhancer (or service) with request-scoped dependencies is built per call, and init/bootstrap hooks fire on that instance.
- **There is no global registration for gRPC enhancers** — no gRPC counterpart to `use_global_http_guards` and friends. Enhancers attach at the impl or method level. `use_global_error_observer` does apply: observers see gRPC guard rejections, errors, and recovered panics like on every other transport.
